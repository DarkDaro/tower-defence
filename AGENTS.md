# ПАМЯТКА АГЕНТУ: правила работы и дисциплина git

Версия 1.0 · 2026-11-02 · для ИИ-агентов, подключаемых к проектам DarkDaro.
Хозяин проекта: **DarkDaro** <legendofworldswarcraft@gmail.com>.
Памятка универсальная — годится для любого нового проекта (не только сайта/игры).
В новый репозиторий кладётся копией под именем `AGENTS.md` в корень.

---

## 1. С ЧЕГО НАЧИНАЕТСЯ СЕССИЯ (чек-лист)

1. Прочитать доки состояния проекта: `docs/state.md` (почему так и текущая картина),
   `docs/dev-log.md` (хронология и открытые вопросы), `README.md` (визитка).
   Работать по памяти прошлых сессий нельзя — только по актуальным файлам.
2. Свериться с remote — в репо могли появиться свежие коммиты:
   ```bash
   git fetch origin && git status -sb && git log --oneline -5
   ```
3. Дерево должно быть чистым. После переноса на другую машину — фантомные
   изменения прав: `git config core.filemode false`.
4. Сверить план работ с хозяином. Сам по себе задачи не выдумывать:
   нет запроса — нет правки. Сомнение — спросить, а не додумать.

## 2. ПРАВИЛА АГЕНТА (дисциплина)

- **Атомарные чанки.** 1 чанк = 1 тема = 1 коммит + запись в `docs/dev-log.md`.
  Работаем мелкими чанками по просьбе хозяина — никаких мегапатчей «всё сразу».
- **Сначала план, потом работа.** Каждое требование хозяина попадает в TODO-план
  (все части, все deliverable, все упомянутые цифры и имена). План озвучивается
  до старта. Не останавливаться, пока каждый пункт плана не закрыт.
- **Ничего не выдумывать.** Факты, числа, даты, цитаты — только из кода, замеров,
  расчётов или слов хозяина. Не знаешь — так и скажи, пометь как допущение.
- **Не выходить за рамки запроса.** Не рефакторить то, что не просили; не менять
  технологии проекта (проект без сборки/модулей — не предлагать сборку/модули);
  чужие решения (архитектура, нейминг, стиль) не переворачивать без запроса.
- **Баланс/настройки — только по замеру.** Правки чисел делаются по протоколу
  «замер до → правка → замер после», один слайд за раз. Протокол замера — в доках
  проекта. Без цифр до/после правка баланса не коммитится.
- **Проверяй живьём.** Пайплайн — необходимое, но не достаточное: `node --check` /
  `py_compile` не ловят потерянные переменные и рассинхрон UI. Каждый чанк,
  меняющий поведение, проверяется живым запуском (headless-браузер, прогон, скриншоты,
  консоль без ошибок). Скриншот ловит то, что глаза в коде пропускают.
- **Доки — часть чанка.** `state.md` — «почему так» и соглашения; `dev-log.md` —
  хронология решений + «открытые вопросы»; README — визитка под текущее состояние.
  Код без актуальных доков = незакрытый чанк.
- **Ничего не удалять.** Старые версии → `Archive/`; перегенерируемые файлы
  достаточно держать в истории git. Удаление — только по явной просьбе хозяина.
- **Отчёт по чанку:** 2–4 строки — что сделано, хеш коммита, что дальше.
- **Конец сессии:** всё закоммичено, запушено, доки актуальны, хозяину — итог.

## 3. РАБОТА С GIT

### 3.1 Коммиты
- Ветка — `main`, пуш только в неё (другие ветки — по отдельной договорённости).
- Сообщения: короткие, по-русски, от лица хозяина, с префиксом темы:
  `мобилка: …`, `баланс: …`, `конфиг: …`, `мета: …`, `звук: …`.
  В теле коммита — что сделано и почему, одной-тремя строками.
- **1 коммит = 1 причина.** Amend — только пока коммит не запушен; после пуша —
  новый фикс-коммит (и пометка в dev-log, если менялись хеши в доках).
- `git add -A` — только после `git status`: не тащить в коммит мусор
  (токены, бэкапы, временные файлы, артефакты тестов).

### 3.2 Пайплайн перед коммитом
```bash
bash scripts/pipeline.sh   # зелёный = можно коммитить; красный = чанк не закрыт
```
Базовые проверки: синтаксис js/py, битые ссылки в разметке, скобки CSS,
следы правок (TODO/FIXME/конфликты). Для нового проекта — адаптировать под его
стек; суть одна: ловить то, что ломает запуск, ДО коммита.

### 3.3 Пуш и токен (важно)
- **Токен живёт в постоянной зоне воркспейса**: файл `/home/z/my-project/.gt`,
  права `600`, в `.gitignore`. Срок жизни ~7 дней — потом хозяин выдаёт свежий.
- Токен **нельзя**: печатать в чат, коммитить, вшивать в remote URL, оставлять
  в логах. В выводах маскировать (например, `sed 's/:[^@]*@/:***@/'`).
- Пуш — только через askpass-обвязку (токен не попадает ни в config, ни в argv):
  ```bash
  # scripts/git_askpass.sh — отдаёт логин x-access-token и токен из .gt
  # scripts/push_td.sh — обёртка: GIT_ASKPASS=…git_askpass.sh git -C <репо> push origin main
  bash /home/z/my-project/scripts/push_td.sh main
  ```
  `push_td.sh` привязан к конкретному репо (tower-defence) — для нового проекта
  скопировать в `scripts/` проекта и поправить путь `git -C`.
- Если `.gt` отсутствует или пуш падает на авторизации — **не обходить**, а
  запросить свежий токен у хозяина и положить в `.gt` (`chmod 600 .gt`).
- Подозрение на «Everything up-to-date» при наличии локальных коммитов:
  `git fetch` и сверить с `origin/main`, не верить первому ответу.
- **Утёкший токен = скомпрометированный токен**: `git rm --cached`, проверить
  `.gitignore`, перевыпустить токен. Не надеяться на «никто не видел».
- Незапушенных коммитов не копить: пуш сразу после зелёного пайплайна.

### 3.4 Подключение нового проекта (чек-лист, ~15 минут)
1. `git init` (или клон пустого репо), ветка `main`.
2. Первым коммитом — `.gitignore`: `.gt`, `.env`, `node_modules/`, `__pycache__/`,
   `*.bak`, файлы сейвов/кэша проекта.
3. `README.md` (визитка: что это, как запустить, управление) +
   `docs/state.md` (соглашения, «почему так») + `docs/dev-log.md` (хронология).
4. `scripts/pipeline.sh` под стек проекта.
5. Пуш-обвязка: скопировать `git_askpass.sh`, сделать свой `push_<имя>.sh`.
6. Токен: запросить у хозяина → `.gt` в корне воркспейса → пробный пуш.
7. Первая запись в dev-log: «проект поднят, обвязка работает».

## 4. СЕКРЕТЫ И БЕЗОПАСНОСТЬ

- Секреты живут только в файлах **вне git** (`.gt`/`.env` + `.gitignore`), права 600.
- Не печатать значения секретов в чат, логи, коммиты, доки; маскировать в выводах.
- Не читать чужие переменные окружения/процессы, не пересылать секреты наружу.
- Прежде чем коммитить `git add -A` — глазами пробежать список файлов.

## 5. КАРТА ВОРКСПЕЙСА

| Путь | Что это |
| --- | --- |
| `/home/z/my-project/repos/<проект>/` | git-проекты (рабочие копии) |
| `/home/z/my-project/.gt` | токен GitHub (постоянная зона, 600, вне git) |
| `/home/z/my-project/scripts/git_askpass.sh` | askpass-хелпер: отдаёт токен git'у |
| `/home/z/my-project/scripts/push_td.sh` | пуш-обвязка tower-defence (образец для новых) |
| `/home/z/my-project/download/` | артефакты, которые нужно отдать хозяину файлами |
| `/home/z/my-project/upload/` | входящие файлы хозяина (не изменять на месте) |

## 6. ПАМЯТКА В ОДНУ СТРОКУ

Сверился с remote → план → мелкий чанк → живая проверка + pipeline → доки →
коммит (префикс) → пуш → отчёт 2–4 строки. Токен не светим, лишнее не трогаем,
числа не выдумываем.
